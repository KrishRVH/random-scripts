Default paved road

Python 3.14 · Django 5.2 LTS · HTML + HTMX · PostgreSQL · S3 · Postgres-backed jobs · managed container runtime

Primary rule

Do not add a boundary, service, or language until a measured requirement clearly pays for it.

Recommended default stack

The broadest practical stack with the least accidental complexity

For most applications — especially CRUD-heavy products, internal tools, operational systems, portals, and AI-assisted business software — the sweet spot is a modular Django monolith with server-rendered HTML, HTMX, PostgreSQL, S3-compatible storage, Postgres-backed background work, and one deployment image. Agent-friendliness comes mostly from reducing boundaries and making the repository deterministic.

Why this wins

It maximizes coverage per unit of complexity. The default stack solves a very wide class of products without introducing a second application language, a frontend build system, multiple stateful stores, or a microservice topology.

What it excludes on purpose

React SPA, Redis, Kafka, OpenSearch, ClickHouse, Kubernetes, service mesh, and dedicated vector infrastructure are all graduation options, not default commitments.

Where agent-friendliness comes from

Predictable structure, one canonical check command, real integration tests, obvious domain entry points, and fewer boundaries to load into context.

    Agent-friendly development

    The repository contract matters as much as the tech stack

    Agents work best when the codebase has one obvious shape, strong machine feedback, and no hidden write path. This is the operating contract that makes the stack actually agent-friendly.

    One write path

    Git is the control plane

    Agents propose changes as diffs. Production changes happen through reviewed commits, typed operational tools, or both.

    One check command

    just check

    Formatting, linting, type checks, migrations, tests, security checks, and integration tests should be reachable through one canonical command.

    Obvious domain entry points

    No invisible behavior

    Prefer explicit service functions over behavior dispersed across signals, hooks, middleware, and import-time side effects.

    Real feedback loops

    Use actual PostgreSQL in integration tests

    Do not let mocks declare success for behavior the real system rejects. Deterministic feedback is part of the product.

    Boundary discipline

    Only add contracts where boundaries exist

    Use OpenAPI for mobile, external, or independently deployed clients — not as an unnecessary boundary between Django templates and the same server.

    Scoped autonomy

    Agents get narrow powers first

    Allow repository edits, analysis, test execution, and pull requests first. Grant wider operational powers only after proven eval history.

    Decision notes

    Frequently argued tradeoffs

    Why Django instead of FastAPI as the center of the stack?

    FastAPI is excellent at typed API edges, but the objective here is widest total coverage with least complexity. Django gives you auth, admin, forms, ORM, migrations, sessions, templating, and a mature project shape. FastAPI is a good addition for narrowly justified API edges, not the best default center for a broad application stack.

    Why HTML + HTMX instead of React by default?

    Because most business software does not need a client-side state architecture. The SPA path forces a second language, a build pipeline, an API boundary, client caching behavior, and more failure modes. Add React only when the product really needs rich client-owned interaction.

    Why PostgreSQL for so many jobs?

    Using PostgreSQL for relational data, JSONB, full-text search, queues, audit trails, outbox tables, and moderate vector workloads minimizes stateful sprawl. Specialized stores can be added later, but broad default coverage comes from consolidating around one strong primary system first.

    Why not Kubernetes as the default runtime?

    Because “containerized” and “needs Kubernetes” are not the same thing. A managed container runtime gives most teams a much better complexity/benefit tradeoff until they actually have many independently scaled workloads or a platform team that can justify the control plane.

    Where do Go and TypeScript still belong?

    TypeScript is the justified second language for rich browser and mobile clients. Go is a justified additional language for hot paths, infrastructure-heavy services, or tools that genuinely benefit from its runtime profile. Neither should be mandatory in the default paved road.

    Bottom line

    The actual thesis

    Optimize for coverage per unit complexity

    Do not confuse a capability catalog with a good default stack. The default should solve the widest common case before any expansion.

    Agent-friendliness is mostly about boundaries

    The best agent stack is usually the one with fewer services, fewer languages, fewer write paths, and stronger machine-readable feedback.

    Expand only on evidence

    React, Redis, Kafka, OpenSearch, ClickHouse, Kubernetes, and dedicated vector stores are all legitimate — just not before the workload proves they are needed.
